How the review loop works

A worked example that also exercises everything the source format supports. Copy it, delete the prose, keep the shapes.

html skill example · stdlib only · 2026-10-20

Everything you need is in this one file. It is written the way a review document should be written: the answer first, in plain language, before any of the detail.

The shape of the thing

A review document is a single HTML file. There is no build step on the reader's side and no network. You select sentences you want to argue with, and your notes travel back to Claude: saved into the file as you type while Claude Code is running, or as one small JSON file when the page is opened on its own.

Think of it as a printed draft with a red pen and a pile of sticky notes. The difference is that the sticky notes know exactly which sentence they were stuck to, so they still line up after the draft is retyped.

Notes are never lost on rebuild

When the document is regenerated, every existing note is searched for by its quoted text. If the sentence moved, the note follows it. If the sentence is gone entirely, the note is kept and labelled Unanchored rather than dropped.

Opened on its own, you click Export yourself

A page opened over file:// cannot write to your disk on its own. Live, a small local server does the saving and Send to Claude wakes the session. Offline, the loop has one human step: press Export notes for Claude, which saves a JSON file.

The loop, end to end

  1. Claude writes plan.src.html and runs reviewdoc.py build --open.
  2. You select text and add notes. Live, each one lands in plan.html as you type.
  3. You press Send to Claude. Offline, you press Export notes for Claude instead.
  4. Claude runs list, then reply on each thread, after an import if you exported.
  5. The answers appear under your comments: live within seconds, offline after a reload.

The panel on the right is the whole interface. Each of your notes becomes a thread, and Claude's answers stack underneath it in order, the way a comment thread works in a word processor.

What the source looks like

The source is plain HTML with a handful of classes. Only < and & need escaping, and build refuses anything outside the vocabulary with a line number, so a slip is never silent.

<h2>A section</h2>
<p>Ordinary <b>bold</b>, <i>italic</i> and <code>vector&lt;int&gt;</code>.</p>
<div class="flag bad" data-pill="the crux">
  <h3>The patch runs after startup</h3>
  <p>Body.</p>
</div>

What each class is for

lede for the opening summary, analogy when a concept needs a real-world hook, flag for anything the reader must not miss, steps for an ordered procedure, card to box up a digression like this one, and a bare <svg> for a diagram.

Things that work well

  • Short sections with one idea each.
  • A diagram wherever a list of facts would otherwise pile up.
  • Naming your own uncertainty, so the reader knows where to push back.

Things that do not

  • Walls of prose with no headings.
  • Jargon that assumes the reader already knows the answer.
  • Burying the recommendation at the bottom.

Ordinary lists nest

  1. A numbered step, with emphasis where it helps.
  2. Another one, dereferencing *ptr and matching *.py without any escaping.
    • A nested detail.
    • And a second nested detail.
  3. Back out to the top level.
